# Review of quiddity-rust at 2fa7207 (2026-10-08)

A whole-repository review (architecture, correctness, tests, maintenance, code) run while the
maintainer was away. Reviewers' findings were re-checked before being recorded here: each says
what was confirmed (re-run or read in the code) and what is the reviewer's measurement only.
The improvement plan at the end is what the next waves of work do about them. Anything that
needs a maintainer decision is listed as a question, not decided.

## High

### H1. CI is red at 2fa7207: a pinned face count depends on float round-off

- **Evidence (confirmed):** CI run 37695256897 on 2fa7207 failed after 18m39s, panicking at
  `tests/correspondence.rs:240`: `("cadgenbench_inputs/cgb207.step", "rot_zx_moved")` is listed
  with 2 faces but gives 1 (face 114 Adapted, area 16.523457 → 16.477808). It was the first CI
  run of `tests/correspondence.rs` (added in d67925c and 2f1765b); earlier green runs predate
  it. `tests/fixtures/known_correspondence.json` pins exact face counts for the cgb207 and
  cgb202 entries, whose own reasons mark the cause rust-wrong: `mass.rs` B-spline and sphere
  face areas change with placement, and whether a face crosses the 1e-3 freeform tolerance
  then depends on the platform's libm. The reviewer reports the commit passing on macOS (not
  re-run).
- **Plan:** short term, a threshold-dependent entry keeps its feature list pinned but gives
  `faces` as an upper bound or a set of acceptable faces; record Linux (CI) as the reference
  platform or add a macOS job. Root cause: H2.

### H2. `mass.rs` face areas are wrong, and depend on placement, for some sphere and B-spline faces; callers read `None` as an area of 0

- **Evidence (confirmed with `examples/face_mass`):** cgb202 face 58 (sphere) gives −20.39 and
  face 994 (sphere) 55.34, where the reviewer gives OpenCascade 9.7675 and 6.2627 (a fine mesh
  agrees with OpenCascade). 46 sphere faces on cgb202 have negative area. cgb207 face 21
  (freeform) gives 1.2102 against 2.2002; faces 109 and 113, a symmetric pair at 6.151 each,
  give 6.234 and 6.279. Callers that default to 0: `gussets.rs:309`,
  `circular_face_patterns.rs:350`, `interior_voids.rs:305`, `thin_walls.rs:389`,
  `levels.rs:168` (`face_mass(..).map_or(0.0, ..)`), and `volume.rs:188` with `solid_mass`.
  Only three `face_mass` uses exist in the kernel tests, all on analytic fixtures.
- **Not re-run:** the OpenCascade and mesh figures; the cgb217 rotated-seam `None` case.
- **Plan:** capture OpenCascade face areas once for the corpus and add a corpus test with
  verdicts (including the reviewer's rust-correct pcurve-versus-3D cases: cgb241 f21, 14052 f1,
  cgb203 f26); check `face_mass` is unchanged under translation and a generic rotation; fix the
  sphere-pole and B-spline boundary walk, starting with cgb202 f58 and cgb207 f21; make the
  `map_or(0.0)` callers refuse or propagate `None`.

### H3. Volume probes count unanswerable rays as air, so `prism_is_empty` can "prove" emptiness through a failure

- **Evidence (confirmed in `crates/haecceity/src/volume.rs`):** `intervals()` (around lines
  529–554) returns an empty `Vec` when `trimmed_hits` is `None` and when parity is still odd
  after four nudges; `pierce` uses `rays.hits(..).unwrap_or_default()` (around 240); `shared()`
  maps any non-`In` state, `Unknown` included, to air in the no-face-box branch (around 393);
  `common_volume` (170) returns a bare `f64`. `src/features/volume_probe.rs:51-53` defines
  `prism_is_empty` as `prism_material_fraction(..) == Some(0.0)`, so a failed probe reads as
  empty. By contrast `classify.rs`'s `State::Unknown` and `rays.rs`'s `crossing_count`
  returning `None` are honest.
- **Plan:** return `Option` from `intervals`, `pierce` and `shared` (for `Unknown`) and
  propagate it, so `common_volume` returns `Option<f64>` and `prism_is_empty` answers false
  when emptiness is unproven. Add a kernel test where a probe meets an unresolvable face and
  refuses. Measure the effect over `tests/probes.rs`.

### H4. Truncated, empty or broken STEP files exit 0 with every family empty

- **Evidence:** `step.rs:684` discards step-io's drop report
  (`let (model, _report) = step_io::read(bytes)`). Confirmed: a header-only STEP with an empty
  DATA section makes `target/release/quiddity` print every family as `[]` and exit 0, where
  Python's `import_step_geometry` raises. Reviewer-reported (not re-run): the same for a deleted
  ADVANCED_FACE in mfcadpp/1008 and for nist_ctc_02 truncated at 60%. `correspond` then reports
  every feature as new.
- **Plan:** `read_step_placed` returns `StepError` when no solid or shell was read, and when the
  report lists a dropped topology or geometry entity reachable from a shape representation. CLI
  tests for the empty-file and deleted-face cases.

### H5. Correspondence fingerprints omit the sizes of several families

- **Evidence (confirmed in `src/correspondence/fingerprint.rs`):** a global list of 32 size
  names (lines 84–117) decides which fields count as sizes; any other numeric field falls to
  `_ => {}`, nested objects are read one level deep, and an array of objects becomes `count`.
  `Plate {axis, lo, hi, u, v}` gives no thickness; `EdgeOpenPrismaticRecess` has
  `run_interval: [f64; 2]` and `section.wall_chain` points; `InteriorVoid.estimated_volume` is
  not listed. Re-run: on `tests/fixtures/edge_open_pocket_floor_hole.step`,
  `edge_open_circular_pockets/0` has traits `{section: present}` and sizes `{}`. The reviewer
  measured empty sizes for all plates (47/47), recesses (6/6) and voids (2/2). A resize can
  therefore be carried without a trace, against R3's "nothing changes without a trace".
- **Plan:** make fingerprint content explicit per family (a per-record method or a family
  table), with a test that classifies every numeric leaf of every family's record as size,
  placement or ignored and fails on an unclassified one. Add plate thickness (hi − lo), the
  run-interval length, pocket section radii and sweep, and void volume; bump
  `FINGERPRINT_VERSION`.

### H6. Corpus kernel checks are skipped on 8 of 100 files because any inventory problem disables them

- **Evidence (confirmed):** `tests/corpus.rs:39-41` runs `check_kernel` only if
  `check_inventory` reported nothing, and `check_inventory` (`tests/common/mod.rs:232-272`)
  returns at the first face problem. `known_divergences.json` has inventory entries for exactly
  8 files (13975, cgb202 "bounds", 14052, ctc_01, ctc_03, ftc_06, ftc_07, ftc_10); six are
  edge-count-only differences (rust-correct seam healing), where face indices still align.
  Reviewer-reported (not re-run): unlisted arc convex/concave flips on cgb202, ftc_07 and 14052,
  mass differences up to 1e-1 and `uv_bounds` differences once the gate is lifted.
- **Plan:** gate `check_kernel` on equal face counts and types, not on an empty inventory
  report; report every inventory problem (or a count and the first few); give each newly
  visible difference a verdict, starting with the arc flips.

### H7. A NURBS ray seed that fails to converge is dropped silently

- **Evidence:** mechanism confirmed in `crates/haecceity/src/nurbs.rs:598-628`: seeds near an
  earlier hit are skipped, and a non-converged Newton seed `continue`s without setting
  `grazing`. `classify.rs:94-99` settles In or Out as soon as two clean rays agree, even when a
  later ray would disagree. Reviewer's reproduction (not re-run): threaded_connector_109 at
  (−54.258, −12.391, 397.522), OpenCascade OUT; face 60 (B-spline) is missed along
  `DIRECTIONS[0]` although inversion puts the surface 6e-14 from OpenCascade's hit at cos 0.82;
  rotated, the classifier says In. Rays disagree on parity at 34 of 500 random points on that
  file.
- **Plan:** a non-converged seed inside the face's box makes the ray ambiguous (set `grazing`,
  or `None` so `crossing_count` discards the ray); refine seeds where the chordal deviation
  exceeds the pad; settle early only when no clean ray so far disagrees. Corpus tests of
  ray-parity agreement, and of the answer against captured BRepClass3d states.

## Medium

### M1. Family wiring is copied by hand with string keys

- **Evidence (confirmed):** `src/features/mod.rs:106-200` stores defining faces under literal
  keys through `kept(&mut defining, "...")`; `fingerprint.rs:151-157` looks them up by the
  serde JSON key; for a family not in `DERIVED` (only hole_patterns and gusset_rib_patterns
  are), `derived_faces` (`fingerprint.rs:177-180`) returns an empty `Vec` with no error. All
  keys match today, but nothing enforces it. `tests/invariance.rs` re-lists each family's
  discover call (line 106 uses the key `thin_walls` where `Features` uses `thin_wall_bodies`),
  and 9c33704 had to fix that file after a merge.
- **Plan:** a unit test that every array key of `serde_json::to_value(&features)` is in
  `DERIVED` or in `features.defining`, with lengths equal to the record counts;
  `derived_faces` fails for a family that is neither; `tests/invariance.rs` uses
  `features::recognise(part).defining`. Consider one families table before the remaining 18
  families.

### M2. Known-difference lists match loosely

- **Evidence (confirmed):** `tests/fixtures/known_probes.json` has six NIST files (ctc_01,
  ctc_03, ctc_04, ftc_06, ftc_08, ftc_09) each with two entries under the identical key
  `_open_channel_section`, one rust-correct and one undetermined; `probes.rs`'s `listed` matches
  by file prefix plus `contains`, so both match the same problems and neither can go stale
  alone. `tests/corpus.rs:68-79` matches by file plus substring (reviewer, not re-run: cgb202
  "evidence" absorbs 6 problems across families, and "bounds" also matches a grooves records
  diff through `body_bounds`). None of the 23 entries in
  `tests/fixtures/captured/known_divergences.json` uses `file` or `options`, so each covers every
  call of its test (`captured.rs:26-30`); the reviewer counts about 34 calls covered against 24
  that diverge.
- **Plan:** each entry gets an exact expected match count, or a key of probe identity, file and
  options, and the test fails on a mismatch; split the duplicated probe entries; fail when a
  problem matches more than one entry.

### M3. The Python reference is not pinned

- **Evidence (confirmed):** `.github/workflows/ci.yml` checks out pzfreo/quiddity (sparse
  `tests/corpus`) with no `ref:`; `calls.json` has only `calls` and `skipped`; `corpus.json`
  records no quiddity revision or file digests. Corpus tests iterate `corpus.json`'s list, so a
  file added upstream is never checked, and a changed file breaks CI on an unrelated commit.
- **Plan:** pin `ref: <sha>` in `ci.yml`; the export and capture tools write the quiddity
  revision and a sha256 per corpus file into their fixtures; a test checks the digests and that
  the files on disk equal `corpus.json`'s list.

### M4. draftwright-rust's handoff describes this repository as of several commits ago

- **Evidence (confirmed):** draftwright-rust `docs/next-session.md:8` says "pushed at 590cb89"
  (HEAD is 2fa7207), line 15 says 22 families (28 entry points now), line 22 says
  correspondence "is not implemented yet" (it was, in d67925c and 2f1765b); `docs/plan.md:196`
  and `docs/model.md:65` are likewise stale.
- **Plan:** refresh those documents, recording the commit each claim describes (a

### M5. Recognition output is not yet consumable by draftwright-rust

- **Evidence (confirmed):** `src/features/mod.rs:91-93` marks `defining` `#[serde(skip)]`; the
  output carries only `fingerprint_version`, with no recognition schema version and no record
  type names. draftwright-rust depends on haecceity only; its `src/bridge.rs` keys on Python
  record type names (e.g. `HoleRecord`, line 108) and defines its own fingerprint
  (`draftwright-bridge/2`, line 29), although R3 says quiddity owns fingerprints. R4 ADR3-4
  (fail closed on family, record type and schema version) is marked pending. Planned
  integration work rather than a defect.
- **Plan:** a versioned recognition document: a schema version and, per record, its family,
  record type, sorted defining faces and parameters, shaped like `bridge.rs`'s `Record`, so
  draftwright can depend on the quiddity crate and switch family by family. Whether draftwright
  drops its own fingerprint is a maintainer question (R3).

### M6. Unresolved STEP geometry is silently substituted

- **Evidence (confirmed):** `step.rs:171` has
  `resolved.unwrap_or(Surface::Other { kind: "UNRESOLVED" })` (NaN evaluation); `step.rs:475-480`
  replaces an unresolved curve with `Line { dir: end - start }`, which is zero for a closed
  edge; `RayCaster::any_hit` (`rays.rs`, around 147) skips a face whose `ray_hits` is `None`, so
  an unsupported face never occludes, while `hits()` returns `None`. Nothing records the
  substitution on the `Part`. The reviewer found no occurrence over 172 corpus and fixture files
  (latent), and reports that replacing 1008's hole circles with hyperbolas leaves the CLI at
  exit 0 with `face_mass` `None` (not re-run).
- **Plan:** `StepError::Unsupported` for an unresolvable closed edge, or record unresolved faces
  and edges on the `Part`; `solid_is_valid` / `common_valid_solid` refuse such solids, HLR
  reports rather than draws, and `any_hit` treats an unanswerable face as unknown. A small
  fixture pins it.

### M7. Corpus-scale tests are serial single-test loops

- **Evidence:** structure confirmed: `correspondence.rs`, `invariance.rs`,
  `crates/haecceity/tests/probes.rs` and `drawings.rs` each loop over the corpus sequentially in
  one `#[test]`. Reviewer timings (not re-run): correspondence 191–233 s, invariance 78–86 s,
  probes 59–68 s, drawings 43 s. CI run 37695256897 took 18m39s (confirmed).
- **Plan:** per-file work under `std::thread::scope` over chunks, results merged sorted by file
  name so output stays deterministic; optionally fold the invariance signature into the
  correspondence loop so each moved part is recognised once.

### M8. Recognition depends on orientation under a generic rotation

- **Evidence:** confirmed that `tests/invariance.rs`'s motions (lines 8–32) are only signed
  permutations plus one translation. Reviewer-measured (not re-run): 260 family changes at a
  37° rotation (fillets on cgb202 288 → 0, interior voids appearing), and Python does the same,
  so the verdict is equivalent. The CLI gives no signal that a part is not aligned with its
  principal axes.
- **Plan:** a maintainer question (report, refuse or canonicalise a non-aligned part).
  Meanwhile add a generic rotation to `invariance.rs`, its differences listed as equivalent in
  `known_invariance.json`.

### M9. 42 Python calls that failed to capture are left out of the reported coverage

- **Evidence (confirmed):** the `skipped` map in `tests/fixtures/captured/calls.json` totals 42
  "capture failed: RuntimeError" entries (turned_steps 18, through_steps 7, plates 4, grooves 3,
  1–2 each for seven more). `captured.rs` never reads `skipped`; the README denominators exclude
  them. The plugin keys a skip by function and exception type only.
- **Plan:** record the test node and message per skip in `capture_plugin.py`; `captured.rs`
  prints and pins the skipped counts per family; the README table shows them.

## Strengths

- The haecceity crate has no dependency on quiddity's feature concepts: a clean one-way
  layering that draftwright-rust shares.
- Every family has one shape: a `recognise_*` entry point mirroring Python over a
  `discover(ctx)` returning occurrences with defining and context faces; shared analysis is
  cached on `Context`, topology on `Part`.
- Doc comments cite the Python or OpenCascade counterpart, so call-by-call auditing is
  greppable.
- All six known-difference lists require a verdict from the five-value set and a reason, and
  fail on stale entries. `known_correspondence.json` pins the exact features and face count per
  case — the model the other lists should follow.
- Strong external oracles: captured Python call replay, the 100-part corpus, rigid-motion
  invariance, OpenCascade drawing comparisons; `QUIDDITY_CORPUS_REQUIRED=1` in CI.
- Honest kernel primitives to build on: `State::Unknown`, and `crossing_count` returning `None`
  for tangent or edge contacts.
- Strict CI: actions pinned by SHA, `fmt --check`, clippy `-D warnings` on all targets, a
  toolchain file.
- Deterministic output in practice: byte-identical CLI JSON across repeated corpus runs.
- Lean, permissively licensed dependencies, compatible with Apache-2.0 and AGPL-3.0.

## Questions for the maintainer

- A part not aligned with its principal axes (M8): report, refuse or canonicalise?
- Should fingerprints use only verified occurrences (L6)?
- Should draftwright-rust drop its own bridge fingerprint once quiddity's recognition document
  exists (M5, R3)?
- Reference platform for float-threshold pins (H1): Linux (CI) only, or a macOS job too?
- Face areas (H2): `known_face_areas.json` records the port's area as rust-correct wherever it
  is confirmed to integrate the region the 3D edges bound and OpenCascade differs only by
  integrating the face's pcurves. README's "What parity means" covers pcurves OpenCascade
  builds on import; does it extend to pcurves the file itself supplies (most cadgenbench
  faces), or should those faces be `equivalent` (the difference is mostly within the edges'
  tolerance strip, which each entry states)?
- Face areas under motion (H2): `face_areas.rs` checks 1e-9 as asked and pins four B-spline
  faces that move by 1.6e-9 to 2.2e-8; seven more move by 1e-10 to 1e-9. Keep 1e-9 with pins
  (which may differ on Linux), or loosen to 1e-7, where any placement-dependent walk still
  shows (those were 1e-5 and above)?
- Unresolved geometry in drawings (M6): `hlr` refuses the whole drawing when any drawn face or
  edge is unresolved. Should it instead draw the resolved faces and return the unresolved ones
  alongside? And should the recognition JSON carry unresolved geometry (today only a stderr
  warning, exit 0)?
- Plates (H5 follow-up): Python places each clustered face group at its lowest coordinate, so a
  plate's thickness changes with motion when faces lie within the 0.5 mm tolerance. Keep parity,
  or cluster symmetrically?
- Captured-call skips (M9): a full recapture with every family re-verified (4210 calls against
  2482, 685 call identities gone), or recapture family by family?
- Recognition document identity (M5): `quiddity-rust/recognition/1` carries the part's face
  count but not the STEP file's sha256, which draftwright's bridge checks (`source_sha256`);
  hashing needs a new dependency (`sha2`, which draftwright-rust already uses). Add it to
  quiddity, or leave the file check to draftwright, which hashes the file it reads anyway?
